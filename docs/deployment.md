# Deployment runbook

For whoever puts this game on Vercel + MongoDB Atlas. It assumes no knowledge of the code: every
step is written for an operator with the owner's accounts. Where a decision's *why* matters, the
ticket that made it is linked, and the reason is repeated here so this file can be read alone.

The one command that must be green before deploying is **`pnpm verify`** (§7).

## Blockers — read this first

Things that stop a deploy, or make one wrong, beyond "you need the credentials". Each appears in
full below.

1. **EU region, both sides.** `vercel.json` pins the function region to Frankfurt (`fra1`); the
   Atlas cluster must be created in AWS **Frankfurt (`eu-central-1`)**. If the Vercel dashboard
   overrides the region with a US one, or the cluster is created in the US, the game processes data
   outside the EU — which the privacy policy and [ticket 12](../.scratch/mvp/issues/12-privacy.md)
   say never happens.
2. **Node.js 22.x.** The function runtime is pinned to `nodejs22.x` in `svelte.config.js` and the
   build to `22.x` in `package.json`. Vercel supports 22 and 24; **Node.js 20 is discontinued
   2026-10-01**. The local dev toolchain (Node 26) is deliberately *not* a Vercel runtime — don't
   match it.
3. **Cron plan limits.** On **Hobby**, cron jobs run **once a day**, anywhere inside the scheduled
   hour, and only on the **production** deployment. `0 3 * * *` (03:00 UTC) is daily, so it is
   allowed; any sub-daily expression fails a Hobby deploy with *"Hobby accounts are limited to
   daily cron jobs"*. Pro lifts that limit and tightens timing to the minute.
4. **Vercel plan terms.** Hobby is for personal, non-commercial projects. If this game ships
   commercially, use Pro; that also removes the cron constraints above.
5. **Atlas network access.** Vercel functions have no static egress IP on Hobby or Pro, so the
   Atlas IP access list has to allow `0.0.0.0/0`. Without an entry, every database call fails after
   the driver's 5-second server-selection timeout. Static egress is an Enterprise/Secure Compute
   feature.
6. **A missing `MONGODB_URI` makes production refuse to serve.** Outside development the app will
   not fall back to the in-process store: every request fails fast instead of playing with progress
   that dies at cold start. §6.6 confirms the URI is really being used.
7. **`PROFILE_PEPPER` is required in Preview too.** Preview deployments are production builds; if
   the pepper is scoped to Production only, every preview URL 500s on its first request.
8. **A missing `CRON_SECRET` fails closed.** `/api/cron/retention` refuses every request without
   it, so the 12-month deletion the privacy policy promises never happens — silently, because
   nobody watches a cron that never runs.

## 1. Prerequisites

- A Vercel account that can create a project, a MongoDB Atlas account, and push access to the repo
  at `origin` (`https://github.com/ionutale/financial-game.git`; adjust if the remote moves).
- A password manager entry ready for the pepper (§3).
- pnpm 12.6.0 locally — `corepack enable` reads the `packageManager` field in `package.json` — and
  a fresh install: `pnpm install`.
- `pnpm verify` green on the exact commit being deployed (§7).
- Optional: the `vercel` CLI (`pnpm dlx vercel`) and `mongosh`.

## 2. MongoDB Atlas — cluster, user, connection string

All of this happens in the Atlas UI at [cloud.mongodb.com](https://cloud.mongodb.com). (If you use
the Atlas CLI, `atlas setup` walks through the same steps; this runbook describes the UI.)

1. Create a project, e.g. `financial-game`.
2. **Build a Database → M0 (Free)** — Flex if the game outgrows the 512 MB free tier later. Cloud
   provider **AWS**, region **Frankfurt (`eu-central-1`)**.
   - If M0 is not offered in Frankfurt, use **Paris (`eu-west-3`)** and change `"regions"` in
     `vercel.json` to `["cdg1"]` so the two stay co-located. Never pick a non-EU region.
   - *Why:* the privacy policy says data does not leave the EU, so no transfer mechanism is needed
     ([ticket 12](../.scratch/mvp/issues/12-privacy.md)); Frankfurt also satisfies ticket 06's
     latency requirement that functions and the cluster sit in the same region.
3. Name the cluster `financial-game` (or accept the default; the name only appears in the SRV
   record, nothing in the code depends on it).
4. **Security → Database Access → Add New Database User**: username `financial-game-app`, an
   autogenerated password, and the role *Read and write to any database* (or a scoped `readWrite`
   on the `financial-game` database — the app never touches another). Atlas will not show the
   password again; it goes straight into the connection string next.
5. **Security → Network Access → IP Access List → Add IP Address**: `0.0.0.0/0`, comment
   *"Vercel functions — dynamic egress"*. This is the only workable option without Vercel Secure
   Compute.
6. **Connect → Drivers → Node.js**, copy the `mongodb+srv://…` string, put `financial-game` in the
   path and keep the default options:
   ```
   mongodb+srv://financial-game-app:<password>@<cluster>.mongodb.net/financial-game?retryWrites=true&w=majority
   ```
   URL-encode any of `: / ? # [ ] @` that occur in the password (`@` → `%40`, and so on).
7. Optional smoke test:
   ```sh
   mongosh '<the string>' --eval 'db.runCommand({ ping: 1 })'   # → { ok: 1 }
   ```
8. Connection budget: the app opens at most **5** connections per function instance
   (`maxPoolSize: 5` in `src/lib/server/mongo-store.ts`) against M0's ~500. Ample for the MVP; if
   Atlas ever reports connections climbing, that is the first number to look at
   ([ticket 06](../.scratch/mvp/issues/06-architecture.md)).

M0 has **no cloud backups**. The stored game state is anonymous and expendable, which is why that
is acceptable — but it means deleting the cluster is final.

## 3. The two secrets

Generate both the same way:

```sh
openssl rand -base64 32 | tr -d '\n'
```

That is 32 random bytes, base64 (44 characters); `tr` strips the newline so the value cannot pick
up whitespace. Any printable string works, but no leading or trailing spaces.

### PROFILE_PEPPER — set once, never rotate

The cookie value never reaches the database: the app stores only `SHA-256(pepper + ":" + cookie)`
as the profile key. The pepper is the server-only secret that makes those digests useless to anyone
who sees the collection.

- Keep a copy in the password manager **before** putting it in Vercel: a Vercel *Sensitive*
  variable cannot be read back, and losing the pepper is the same as rotating it.
- **Consequence of rotating:** every digest already stored stops matching. Players keep their
  cookie, but it now points at nothing, so their next visit silently starts a fresh profile at
  month 1 — progress and replays are unrecoverable. The orphaned documents are not deleted by the
  rotation; the retention sweep still removes them 12 months after their last activity. Nothing is
  corrupted, only lost. Rotation is a v2 problem, deliberately not built
  ([ticket 12](../.scratch/mvp/issues/12-privacy.md)).
- Required in Production **and** Preview. Without it, the first request to any route throws
  (`profilePepper()` in `src/lib/server/env.ts` refuses to fall back to the dev value outside dev).

### CRON_SECRET — rotatable at any time

Vercel automatically sends `Authorization: Bearer <CRON_SECRET>` when it invokes the retention
cron; the route compares it in constant time and fails closed if the secret is unset or wrong.

- Rotating is safe: replace the variable, and the next invocation uses the new value. No data is
  derived from it, unlike the pepper.
- Vercel recommends at least 16 characters; the generated value is longer.
- Generate it once for Production. A Preview copy is harmless but unused — cron runs only against
  production.

## 4. The Vercel project

1. **Import.** Dashboard → Add New → Project → import the GitHub repo (or `vercel link` in the repo
   and `vercel --prod` for the first deploy). Framework preset: SvelteKit, auto-detected. Install
   uses the pinned pnpm because of `packageManager`; build is `pnpm build`.
2. **Node.js Version: 22.x.** `engines.node` in `package.json` pins it; confirm under Settings →
   General. This matches CI (`.github/workflows/*.yml`) and the function runtime.
3. **Function Region: Frankfurt.** `vercel.json` pins `"regions": ["fra1"]`; confirm Settings →
   Functions shows Frankfurt and that nobody has overridden it there. Hobby allows exactly one
   region, which is all this app uses.
4. **Environment variables** (Settings → Environment Variables). Add all three, mark each
   **Sensitive**, and scope each to **Production and Preview**:

   | Name | Value | What it does | If it is missing |
   |---|---|---|---|
   | `MONGODB_URI` | the Atlas SRV string from §2 | the only persistent store; a module-scope `MongoClient` with a small pool, reused across invocations | every request fails fast: a production build refuses the in-process store (ticket 32) |
   | `PROFILE_PEPPER` | §3, from the password manager | peppers the profile digest; never changes | every request to every route throws 500 |
   | `CRON_SECRET` | §3 | authorises the daily retention sweep | `/api/cron/retention` 401s forever; the 12-month deletion stops |

   *Preview note:* preview URLs share the cluster, database and pepper by default, so preview play
   writes rows that production's sweep also cleans up. If you want previews isolated, point the
   Preview-scoped `MONGODB_URI` at a `financial-game-preview` database — but then preview data is
   never swept and must be removed by hand.
5. **Cron Jobs.** After the first deploy: Settings → Cron Jobs should list `/api/cron/retention` at
   `0 3 * * *` UTC. If it does not, `vercel.json` was not the file deployed — redeploy it.

## 5. First deploy

- Git path: push to the project's Production Branch (usually `master` here). CLI path:
  `vercel --prod`.
- The build runs `prepare` (SvelteKit sync + Paraglide compile) and then `vite build`;
  adapter-vercel emits Node functions on `nodejs22.x`. Nothing else needs a build setting.
- A first deploy is not finished until §6 passes on the production URL.

## 6. First-deploy verification

Set `PROD` once and run everything against the deployed URL:

```sh
PROD=https://<your-production-domain>   # no trailing slash
```

**6.1 It is up, and English by default**

```sh
curl -s "$PROD/" | grep -o '<html lang="[^"]*"'
# <html lang="en"
```

**6.2 The profile cookie is correct** — 32 random bytes, `httpOnly`, `Secure`, `SameSite=Lax`,
one year:

```sh
curl -sI "$PROD/" | grep -i '^set-cookie'
# fg_profile=…; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=31536000
```

Because it is `Secure`, test on the HTTPS URL; a production build over plain HTTP will not keep it.

**6.3 The locale routes are real** — the prefix is stripped before routing and the document is
translated ([ticket 26](../.scratch/mvp/issues/26-i18n-build.md), [ticket
28](../.scratch/mvp/issues/28-language-switcher-ci.md), [ticket
29](../.scratch/mvp/issues/29-localized-internal-links.md)):

```sh
curl -s "$PROD/it" | grep -o '<html lang="[^"]*"'           # <html lang="it"
curl -s "$PROD/ro" | grep -o '<html lang="[^"]*"'           # <html lang="ro"
curl -s "$PROD/it/settings" | grep -o '<title>[^<]*</title>' # Italian title
```

**6.4 The right of access works** — the export is a downloadable JSON envelope of the active Run
and every replay archive, with no cookie and no digest in it
([ticket 12](../.scratch/mvp/issues/12-privacy.md)):

```sh
curl -s -c fg.jar -o /dev/null "$PROD/"                # mint the cookie
curl -s -b fg.jar "$PROD/api/profile/export" | head -c 400
```

You should see `format`, `version`, `exportedAt`, `run` and `archive` keys (`run: null` until you
play). In the UI, Settings → *Download my data* downloads the same file.

**6.5 The right of erasure works** — deletes the profile's stored data and expires the cookie:

```sh
curl -s -X DELETE -b fg.jar -c fg.jar "$PROD/api/profile"
# {"ok":true}
```

The response carries `fg_profile=; … Max-Age=0`. Export again: empty. In the UI, Settings →
*Delete everything* sits behind the typed confirmation and returns the player to a fresh month 1.

**6.6 Data is really persisting** — this is the check for blocker 6:

Play a month on the deployed site, then Atlas → Deployment → Browse Collections → `financial-game`
→ `runs`. There must be one document whose `_id` is a 64-character hex digest (the peppered key,
never the cookie) and whose `updatedAt` is fresh. **An empty collection means the app is not really
using Atlas — a wrong URI, a closed network access list, or a deploy from before ticket 32 — stop
and fix it before announcing anything.**

**6.7 The cron fails closed, then runs**

```sh
curl -s -o /dev/null -w '%{http_code}\n' "$PROD/api/cron/retention"        # 401
curl -s -H "Authorization: Bearer $CRON_SECRET" "$PROD/api/cron/retention" # {"ok":true,"deleted":0,…}
```

Then trigger it deliberately: dashboard → Settings → Cron Jobs → Run (or
`vercel crons run /api/cron/retention`), and confirm a 200 and a `[retention] deleted N run(s)`
line in the runtime logs. Vercel invokes crons only against the production deployment, in UTC —
and on Hobby, any time inside the 03:00 hour.

**6.8 The code gate passes** — run `pnpm verify` (§7) on the exact commit that was deployed.

## 7. The gate: `pnpm verify`

One command runs the full set, in this order:

| Step | Command | What it proves |
|---|---|---|
| Type check | `pnpm check` | `i18n:compile` + `svelte-kit sync` + `svelte-check`: broken routes, props or types fail here. |
| Unit tests | `pnpm test` | Vitest: game rules, store ordering, cron auth, export payload, retention, i18n. |
| Translation gate | `pnpm i18n:check` | `inlang validate` + `inlang lint` + the deck-integrity test: a missing, orphaned or parameter-drifted key fails. |
| Accessibility | `pnpm a11y` | Builds the production app, serves it, runs axe (WCAG 2.2 AA across nine screens) and Lighthouse (accessibility ≥ 0.95). |

First time on a machine: `pnpm exec playwright install chromium`. The accessibility step serves its
own preview build on port 4173 with `--strictPort` (it fails rather than killing whatever holds the
port); `A11Y_BASE_URL` points it at an already-running server instead
([docs/accessibility.md](accessibility.md)).

CI parity: `.github/workflows/ci.yml` runs the type check and unit tests,
`.github/workflows/i18n.yml` runs the translation gate, and `.github/workflows/a11y.yml` runs the
accessibility gate — each on every push and pull request. `pnpm verify` is all four in one place,
designed to run before a deploy.

## 8. Rollback

- Fast path: Vercel dashboard → Deployments → the last good deployment → **Instant Rollback**, or
  `vercel rollback`. Git path: revert the offending commit and let the normal deploy run.
- What a rollback does **not** touch: environment variables, Atlas data, and **cron jobs** — Vercel
  keeps invoking the schedule from the current project configuration, not from the rolled-back
  code. If the bad deploy changed the schedule, fix it separately.
- Roll back one deployment at a time. Deployments from after [ticket
  23](../.scratch/mvp/issues/23-run-archive.md) can read the current document shape; deployments
  from before it cannot, so don't jump across that line.
- Never "fix" a rollback by rotating `PROFILE_PEPPER` — that orphans every player (§3).
- Re-run §6 on the production URL afterwards; a rollback is not verified until the cookie, export,
  delete and cron checks pass again.

## 9. Operating notes

- **Rotation:** `CRON_SECRET` any time; `MONGODB_URI` when rotating the database password (update
  both environment scopes, then redeploy so functions pick it up); `PROFILE_PEPPER` never in v1.
- **Monitoring:** Vercel runtime logs for 5xx and the `[retention]` line; Atlas alerts for
  connections. There is no analytics and nothing else the game sends — by design
  ([ticket 12](../.scratch/mvp/issues/12-privacy.md)).
- **Abuse:** there is no application-level rate limiting. Ticket 06 suggested a WAF rate-limit rule
  on `/api/run/*` if the deployed URL sees abuse; that is a Vercel Firewall/Dashboard setting (and a
  plan feature), not code.
- **Region changes are migrations, not settings.** Move the Atlas cluster (mongodump/restore; M0 has
  no backup), verify, then change `"regions"` in `vercel.json`, in one maintenance window. Both
  sides stay in the EU.
- **Deleting the Atlas cluster** deletes every profile irrecoverably — it is *Delete everything* for
  all players at once.
