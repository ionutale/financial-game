# 07 — i18n for en / it / ro in SvelteKit 5

Findings for ticket [`07-i18n`](../issues/07-i18n.md). Research date: 2026-09-20.
Constraint in force: **translate-only, one shared economy** — en / it / ro are translations of a single
game world; locale never changes game mechanics, prices, or rules.

---

## Recommendation (short)

1. **Library: Paraglide JS** (`@inlang/paraglide-js`) — it is the **official SvelteKit i18n integration**
   (`npx sv add paraglide`) and its companion ecosystem (Fink editor, inlang CLI, `missingTranslation`
   lint rule) is the only option that makes the 60-card deck translatable **without developer
   involvement**. It is compiler-based, fully typed, tree-shaken, and ships SSR-safe locale isolation.
2. **Do not put event-card text inside the card JSON.** Keep the deck **structural and
   language-neutral** (ids, stage, concept, effects, weights, art) and put every human string in
   `messages/{locale}.json` under **deterministic keys derived from card/choice ids**
   (`card_042_choice_save_feedback`). This is the one layout that makes translation mechanical,
   tooling-readable, and CI-checkable.
3. **Locale-prefixed URLs + a cookie, with browser-language detection as a fallback**
   (`strategy: ["url", "cookie", "preferredLanguage", "baseLocale"]`). Deep links then carry their
   language; the locale switch is a full document navigation that preserves the path.
4. **One currency, three number systems.** Fix the world currency (code `EUR`) and format it with
   `Intl.NumberFormat(locale, { style: "currency", currency: "EUR" })` **passing the app locale
   explicitly**. Same economy, locale-correct grouping/separators/symbol placement.
5. **Three CI gates**: `sv check` (typed keys), `inlang lint` with `missingTranslation` set to
   `error` (untranslated card text), and a Vitest deck-integrity test (every deck card/choice has
   its keys in all three locales; no orphan `card_*` keys).

## 1. Library options for SvelteKit 5

SvelteKit itself provides **no i18n library**. Historically the community answer was
`kaisermann/svelte-i18n`; SvelteKit's own recommended path is now Paraglide.

| Option | Shape | SvelteKit 5 fit | Typed keys / missing-key safety | Translator/CI tooling |
|---|---|---|---|---|
| **Paraglide JS** (`@inlang/paraglide-js`) | Compiler → generated message functions | **Official** integration shipped as a SvelteKit CLI add-on (`npx sv add paraglide`); Vite plugin, `reroute` + `handle` hooks generated; SSR request isolation via `AsyncLocalStorage` | Yes — generated TS/JSDoc declarations, full autocomplete, compile/type errors for unknown keys | **Best**: inlang message format, Fink web editor, inlang CLI (`machine translate`, `lint`/`validate`), Sherlock VS Code, `missingTranslation` lint rule |
| `kaisermann/svelte-i18n` | Runtime stores (`$_('key')`) | Works, but store-based; v4.0.1 published ~2 years ago; README says it is "due to some reworking… from a singleton to instances" | No compile-time key typing; missing keys fall back at runtime | None built in |
| Minimal runes-native libs (e.g. `@nomideusz/svelte-i18n`) | Runtime, `$state` locale + flat JSON | Svelte 5-native, tiny (claims <150 LOC) | Type-loose | Explicitly *not* for large volumes of strings |
| Hand-rolled dictionary + `reroute` | Runtime Map | Works | All missing-key handling is manual | None |

Sources:
- SvelteKit official CLI add-on: <https://svelte.dev/docs/cli/paraglide> ("Paraglide from Inlang is a
  compiler-based i18n library…", what `npx sv add paraglide` scaffolds).
- Paraglide overview: <https://paraglidejs.com/> ("SvelteKit's official i18n integration").
- `kaisermann/svelte-i18n` status: <https://www.npmjs.com/package/svelte-i18n> (v4.0.1, "due to some
  reworking"), <https://github.com/kaisermann/svelte-i18n>.
- Minimal alternative positioning itself away from this use case:
  <https://svelte-i18n-five.vercel.app/docs> ("not intended to replace feature-rich libraries like…
  Paraglide.js… managing large volumes of strings").
- Compiler vs runtime trade-offs (bundle size, tree-shaking, SSR): 
  <https://paraglidejs.com/comparison>, <https://paraglidejs.com/architecture>.

### Why Paraglide wins for *this* game

- **~60 cards × ~6–10 strings ≈ 400–600 messages × 3 locales.** That is a "large text content" app.
  Paraglide compiles each message to its own module and Vite tree-shakes unused ones, so bundle
  size tracks *used* UI strings, not catalog size (<https://paraglidejs.com/compiling-messages>).
- **The tooling is the real prize.** The 60 cards are authored by a writer and translated by
  non-developers; inlang's Fink editor + CLI + lint rules are a purpose-built pipeline over the
  same JSON files the app compiles (see §6).
- **SSR safety matters on Vercel.** The SvelteKit setup routes the request through
  `paraglideMiddleware()`, which scopes locale per request via `AsyncLocalStorage`; the docs
  explicitly say to **keep `AsyncLocalStorage` enabled on Vercel Edge / Node** and to treat
  `disableAsyncLocalStorage` as a last-resort fallback because it can leak locale state between
  concurrent requests (<https://paraglidejs.com/sveltekit>, "Troubleshooting").
- **Typed interpolation.** Message functions are typed, including parameters and — with markup —
  the exact tag names used, so a Svelte `<ParaglideMessage>` snippet is checked at build time
  (<https://paraglidejs.com/markup>).

**Non-recommendation up front:** the deck is *not* a translation format. Do not store
`{ "en": "...", "it": "...", "ro": "..." }` objects inside card JSON — inlang/Fink cannot read them,
so every card edit becomes a developer task, and you lose linting. Paraglide's own docs warn that
folded structured data in message values forces translators to hand-edit syntax and invites runtime
crashes (<https://paraglidejs.com/objects-and-arrays>).

## 2. Content organisation: UI strings **and** the 60 event cards

### 2.1 Two sources of truth, one text catalog

Split content into **structure** (code/data, not translated) and **text** (catalog, translated):

| Concern | Lives in | Translated? |
|---|---|---|
| UI chrome (menus, buttons, HUD labels, Money Story template) | `messages/{locale}.json` | yes |
| Card *structure* (id, stage, concept, weight, art, effect vocabulary references) | `content/cards/*.json` | **no** |
| Card *text* (situation, choice labels, feedback) | `messages/{locale}.json` | yes |

The deck record carries **no** prose:

```jsonc
// content/cards/phase-3-first-job.json  (language-neutral)
{
  "id": "card_042_first_payslip",
  "stage": "first_job",
  "concept": "budgeting",
  "weight": 3,
  "art": "art/payslip.svg",
  "durationMonths": 1,
  "choices": [
    { "id": "save",  "effects": [ { "op": "add", "account": "savings", "amount": 120 } ] },
    { "id": "spend", "effects": [ { "op": "add", "account": "cash",    "amount": 120 } ] }
  ]
}
```

### 2.2 Deterministic text keys

Every string the card needs is a flat key derived from the card id and choice id:

| Key | Rendered where |
|---|---|
| `card_042_situation` | card prompt |
| `card_042_choice_save_label` | choice button |
| `card_042_choice_save_feedback` | post-choice feedback (teaches the concept) |
| `card_042_choice_spend_label` | choice button |
| `card_042_choice_spend_feedback` | post-choice feedback |

```jsonc
// messages/en.json
{
  "card_042_situation": "It's your first payday. The money looks bigger than you expected.",
  "card_042_choice_save_label": "Move 20% straight into savings",
  "card_042_choice_save_feedback": "Saving before you spend is called 'paying yourself first'. The {amount} you moved is now working for you."
}
```

```jsonc
// messages/it.json
{
  "card_042_situation": "È il tuo primo giorno di paga. La cifra sembra più grande del previsto.",
  "card_042_choice_save_label": "Metti subito il 20% da parte",
  "card_042_choice_save_feedback": "Mettere da parte prima di spendere si chiama «pagare prima te stesso». I {amount} che hai spostato ora lavorano per te."
}
```

Why deterministic (not random) keys here: Paraglide *recommends* random human-readable keys for UI
strings because semantic names invite renaming (<https://paraglidejs.com/message-keys>). The card
scheme is the deliberate exception — the **card id is already the immutable identity** (fixed by the
Event Card schema in ticket 03), and the runtime must *derive* the lookup to keep the deck
language-neutral. Treat card ids as database keys: **never rename them**. UI chrome keys can follow
Paraglide's random-key advice.

Interpolation parameters are part of the key's contract (`{amount}`, `{months}`, …). Paraglide
enforces parameter types at compile time for statically written calls
(<https://paraglidejs.com/basics>); for dynamically derived card keys the parameters are checked by
the deck test in §3.

### 2.3 A thin typed accessor layer

Because the card lookup is dynamic, wrap it once so the rest of the app never composes keys:

```ts
// src/lib/game/card-text.ts
import { m, type LocalizedString } from '$lib/paraglide/messages.js';

export type CardText = {
  situation: () => string;
  choices: Record<string, { label: () => string; feedback: () => string }>;
};

export function cardText(cardId: string, choiceIds: string[], amount?: number): CardText {
  const get = (key: string) => (m as Record<string, (args?: object) => string>)[key];
  return {
    situation: () => get(`card_${cardId}_situation`)?.(),
    choices: Object.fromEntries(choiceIds.map((id) => [id, {
      label: () => get(`card_${cardId}_choice_${id}_label`)?.(),
      feedback: () => get(`card_${cardId}_choice_${id}_feedback`)?.({ amount }),
    }])),
  };
}
```

Use Paraglide **markup** (`{#strong}…{/strong}`, `{#amount/}`) instead of raw HTML so translators can
place emphasis and the Svelte renderer owns the tags (<https://paraglidejs.com/markup>). Use the
**`plural`** formatter for count-bearing copy (Romanian has `one`/`few`/`other`, so do not hand-roll
`count === 1` branches) (<https://paraglidejs.com/variants>).

## 3. Catching missing keys in CI

There are **three distinct failure modes**; each needs its own gate.

| Failure | Example | Gate |
|---|---|---|
| Key used in code but not in the catalog | a component calls `m.hud_balance()` that was never added | **`sv check` / TypeScript** — Paraglide generates typed message functions; `emitTsDeclarations: true` keeps the language server in sync (<https://paraglidejs.com/compiling-messages>) |
| Key present in `en` but not translated in `it`/`ro` | `card_042_situation` missing from `messages/ro.json` | **`npx @inlang/cli lint`** with `missingTranslation` raised from `warning` to `error` (<https://inlang.com/m/4cxm3eqi/messageLintRule-inlang-missingTranslation>) |
| Deck references a key that no locale defines | card 042 added but its `card_042_*` keys never authored | **Vitest deck-integrity test** (below) — Paraglide cannot type-check dynamically derived keys |

`project.inlang/settings.json`:

```jsonc
{
  "$schema": "https://inlang.com/schema/project-settings",
  "baseLocale": "en",
  "locales": ["en", "it", "ro"],
  "modules": ["https://cdn.jsdelivr.net/npm/@inlang/plugin-message-format@latest/dist/index.js"],
  "plugin.inlang.messageFormat": { "pathPattern": "./messages/{locale}.json", "sort": "asc" },
  "messageLintRuleLevels": { "messageLintRule.inlang.missingTranslation": "error" }
}
```

Deck-integrity test (`src/content/cards.i18n.test.ts`), run by Vitest in CI:

```ts
import { describe, it, expect } from 'vitest';
import en from '../../messages/en.json';
import it from '../../messages/it.json';
import ro from '../../messages/ro.json';
import { deck } from './index'; // all cards

const catalogs = { en, it, ro } as const;

// 1. every card/choice has all three strings in all three locales
// 2. no orphan card_* keys (deck is the source of truth)
// 3. interpolation parameters match across locales
```

Rules it enforces:

- For each card and choice: `card_<id>_situation`, `card_<id>_choice_<cid>_label`,
  `card_<id>_choice_<cid>_feedback` exist and are non-empty in `en`, `it`, `ro`.
- Parameter sets extracted per key (regex `\{(\w+)\}`) are **identical across locales**; a `{amount}`
  in `en` must not be dropped in `ro`.
- Every `card_*` key in each catalog maps to a card/choice that exists in the deck.

Combine with `validate` (`npx @inlang/cli validate`) to confirm the inlang project is well-formed;
`machine translate --force` is safe for build pipelines but the docs advise using it for drafts, not
as the final translation (<https://inlang.com/m/2qj2w8pu/app-inlang-cli>).

GitHub Actions sketch:

```yaml
- run: pnpm sv check                         # typed message keys
- run: pnpm exec inlang lint --project ./project.inlang   # untranslated strings (error level)
- run: pnpm exec inlang validate --project ./project.inlang
- run: pnpm test                              # Vitest deck-integrity test
```

> Note: inlang's older PR linter action "Ninja i18n" is **deprecated** ("We strongly advise against
> using Ninja for new projects", <https://inlang.com/m/3gk8n4n4/app-inlang-githubLintAction>). Use
> the CLI in CI instead. Sherlock (VS Code) is the editor-side equivalent
> (<https://inlang.com/m/r7kp499g/app-inlang-ideExtension>).

## 4. Routing: locale in the URL vs a locale switch

### Recommendation: locale-prefixed URLs **plus** a cookie

Configure:

```ts
paraglideVitePlugin({
  project: './project.inlang',
  outdir: './src/lib/paraglide',
  emitTsDeclarations: true,
  strategy: ['url', 'cookie', 'preferredLanguage', 'baseLocale']
})
```

With the default pattern, `en` is unprefixed and the others are prefixed: `/game`, `/it/game`,
`/ro/game` (<https://paraglidejs.com/i18n-routing>). Route files stay unprefixed
(`src/routes/game/+page.svelte`); the generated `reroute` hook de-localizes incoming URLs:

```ts
// src/hooks.ts  — MUST be hooks.ts, not hooks.server.ts
import { deLocalizeUrl } from '$lib/paraglide/runtime';
export const reroute = (request) => deLocalizeUrl(request.url).pathname;
```

and `src/hooks.server.ts` wraps the app in `paraglideMiddleware`, injecting `%lang%` / `%dir%` into
`app.html` (`<html lang="%lang%" dir="%dir%">`) — this is exactly what `npx sv add paraglide`
scaffolds (<https://paraglidejs.com/sveltekit>, <https://svelte.dev/docs/cli/paraglide>). SvelteKit's
accessibility guide confirms `lang` should track the current page's language
(<https://svelte.dev/docs/kit/accessibility#The-lang-attribute>).

### Why URL + cookie (not a switch-only locale)

- **Deep links carry the language.** A shared Money Story result, or a resumed `/game` link, should
  open in the sender's language; with a cookie/localStorage-only switch the recipient's first paint
  can be the wrong language, and the stored override is invisible to the server on the first request
  (<https://paraglidejs.com/strategy>, "Prioritize user preferences" note).
- **Machine-readable language per page** enables `<link rel="alternate" hreflang>` and per-locale
  sitemap entries. Paraglide provides `generateStaticLocalizedUrls()` explicitly "for generating
  sitemaps and `<link rel="alternate" hreflang>` tags for SEO"
  (<https://paraglidejs.com/runtime#generatestaticlocalizedurls>). SvelteKit SSR + unique titles/meta
  are the rest of the SEO story (<https://svelte.dev/docs/kit/seo>).
- **Switching preserves the path.** `setLocale()` performs a **full document navigation** to the
  localized URL; the docs warn *not* to use `reload: false` for a normal picker, and to add
  `data-sveltekit-reload` to cross-locale `<a>` links so the server-rendered document, `<html lang>`
  and client state stay in sync (<https://paraglidejs.com/basics>, <https://paraglidejs.com/errors>).
- **Locale is presentation, not game state.** With one shared economy, the locale must never be
  persisted into run data or feed the seeded RNG. Switching language mid-run re-renders text only;
  the run, prices and deck are identical. Keep `locale` out of the Anonymous Profile payload.

SEO is secondary for this product (it is an app, not a content site), but prefixed URLs cost nothing
and make locale explicit for links, support and QA.

## 5. Formatting one economy in three locales

### Currency: one code, locale-driven presentation

The locked decision is **one economy**. So the world uses **one currency identity** and only the
*formatting* changes. Recommended: fix the code to `EUR` and pass it explicitly with the app locale.

```ts
// src/lib/format/money.ts
const cache = new Map<string, Intl.NumberFormat>();
export function money(locale: string, amount: number) {
  let f = cache.get(locale);
  if (!f) {
    f = new Intl.NumberFormat(locale, {
      style: 'currency',
      currency: 'EUR',            // fixed → one economy
      minimumFractionDigits: 0,   // whole-euro game amounts read cleaner
      maximumFractionDigits: 2
    });
    cache.set(locale, f);
  }
  return f.format(amount);
}
```

`Intl.NumberFormat` is the standard, language-sensitive formatter
(<https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat>).
Same money, three renderings:

| Locale | `money('…', 1234.5)` |
|---|---|
| `en` | `€1,234.50` |
| `it` | `1.234,50 €` |
| `ro` | `1.234,50 €` |

Three cautions:

1. **Always pass the locale.** `new Intl.NumberFormat()` *without* a locale uses the runtime's
   locale (on the server, the Node default), producing server/client mismatch
   (<https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/NumberFormat>).
2. **EUR in Romania is a fiction, not a bug.** Romania uses RON in reality; because the decision is
   one shared economy we cannot show `lei` to `ro` users. Two defensible options: (a) **EUR** — the
   currency most likely to be recognisable across all three locales; (b) a **neutral in-game
   currency** with its own symbol, to avoid implying any real market. Pick one in the spec and state
   it explicitly; do **not** make `currency` locale-dependent. (If the writer wants realism, option
   (b) with a well-designed symbol is the cleanest way to honour "one economy".)
3. **Paraglide can format inside messages too** via `amount: number style=currency currency=EUR`,
   which is useful for a sentence like "Balance: {formattedAmount}"
   (<https://paraglidejs.com/formatting>). Keep the currency **literal** in the declaration so
   translators cannot change it.

### Numbers, percentages, dates

- Numbers/percentages: same rule — `Intl.NumberFormat(locale, { style: 'percent' })`, locale always
  explicit; `en` uses `1,234.5` / `12.5%`, `it`/`ro` use `1.234,5` / `12,5%`.
- **In-game time**: model it as `{ year: number; month: 1..12 }`, not a real `Date`. Render the month
  name with `Intl.DateTimeFormat` for locale-correct names, anchored to a **UTC** date, and
  interpolate the numeric in-game year:

  ```ts
  const month = new Intl.DateTimeFormat(locale, { month: 'long', timeZone: 'UTC' })
    .format(new Date(Date.UTC(2025, monthIndex, 1)));
  // en "January" / it "gennaio" / ro "ianuarie"
  ```

  This sidesteps timezones, DST and ICU `dateStyle` drift entirely
  (<https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat>).
  If a full date is ever needed, pin `timeZone: 'UTC'` — Paraglide's formatting guide calls this out
  ("Use an explicit `timeZone` if output must be stable across environments",
  <https://paraglidejs.com/formatting>).

### SSR/hydration and cost

- Format on both server and client with the **same locale and options**; mismatches surface as
  hydration warnings. A single memoized `format/` module (above) is the enforcement point —
  `Intl` formatter construction is comparatively expensive, and Paraglide's docs note formatting runs
  on every message call (<https://paraglidejs.com/formatting>).
- Add **snapshot tests per locale** for the handful of formatters (`money`, `percent`, `monthName`)
  so an ICU/Node upgrade that changes spacing or symbol placement fails loudly rather than silently
  shifting the UI.

## 6. What a translator needs (and doing 60 cards without a developer)

### Pipeline

1. **Writer authors English only** into `messages/en.json` (plus the structural deck). Card ids are
   frozen here.
2. **Machine draft**: `npx @inlang/cli machine translate --project ./project.inlang` fills `it.json`
   / `ro.json` (free community service by default; BYO Google/DeepL key for reliability). The docs
   explicitly frame this as draft generation, warning against unattended pipeline use for final copy
   (<https://inlang.com/m/2qj2w8pu/app-inlang-cli>).
3. **Human review in Fink** — the inlang CAT web editor at <https://fink.inlang.com/>. The repo
   remains the source of truth; "translators do not need to work in the repo" — editor apps operate
   on the same localization data (<https://inlang.com/docs>; Fink:
   <https://inlang.com/m/tdozzpar/app-inlang-finkLocalizationEditor>). Fink is **free beta** today,
   with a note to upvote a full SDK-v2 release (<https://inlang.com/m/tdozzpar/app-inlang-finkLocalizationEditor>).
4. **CI gate**: `inlang lint` (missing translation = error) + `validate` + the deck test block a merge
   with any untranslated card (§3).
5. **Sherlock** (VS Code) gives in-editor decorations/hover for developers while adding strings
   (<https://inlang.com/m/r7kp499g/app-inlang-ideExtension>).

### Translator context (the part 60 cards really need)

A bare key like `card_042_choice_save_feedback` is untranslatable without the scenario. Provide
context **outside the code** via a generated brief:

- `docs/translation-brief.md` (or `content/cards/translation-brief.md`), regenerated from the deck,
  listing per card: stage, concept taught, the situation in one line, what each choice does
  mechanically, and the feedback's teaching point.
- A short **tone/voice note** (teen, modern, non-moralising — ticket 03's authoring rules) and a
  **glossary of the eight Concepts** (from `CONTEXT.md`) with their approved it/ro terms, so the same
  concept is named identically on every card.
- **Length limits** from ticket 03, restated for translators (mobile-first: feedback text must fit a
  card without scrolling on a 360 px viewport). This is the main translation-quality risk: Italian and
  Romanian runs longer than English.

The en/it/ro pair is also small enough that **TMs/glossaries are unnecessary**; a shared glossary in
the brief is sufficient.

## 8. Decisions this forces on other tickets

- **Ticket 03 (Event Card schema)** — remove per-locale text fields ("locale strings for en/it/ro").
  Replace with a documented key convention: `card_<id>_situation`,
  `card_<id>_choice_<choiceId>_{label,feedback}`, plus a rule that **card ids are immutable**.
- **Ticket 06 (architecture)** — the deck is language-neutral; text is compiled into the app at build
  time by Paraglide, so the "content delivery" question becomes "ship structural cards, text is
  bundled". Keep Paraglide's `AsyncLocalStorage` enabled on Vercel.
- **Ticket 11 (spec assembly)** — pin the currency decision (§5, option a or b), the strategy array,
  and the three CI gates.

## 9. Risks / open questions

1. **Fink is beta.** Have a fallback: translators edit `messages/it.json` / `messages/ro.json`
   directly (or via a PR) and CI still protects completeness. The catalog format is plain JSON, so
   nothing is locked to Fink.
2. **Machine-translate provider stability.** The default community service is "not guaranteed";
   budget for a Google/DeepL key if translation is routine (<https://inlang.com/m/2qj2w8pu/app-inlang-cli>).
3. **Currency fiction (§5).** Needs an explicit product decision; it is the one place "translate-only,
   one economy" visibly bends reality.
4. **Romanian plural categories.** Use `Intl.PluralRules`-backed `plural` variants, not `count === 1`.
5. **Text length on mobile.** Enforce ticket 03's limits in the source and give translators a rule of
   thumb (e.g. aim for it/ro ≤ ~115% of the English length previewed in Fink).
